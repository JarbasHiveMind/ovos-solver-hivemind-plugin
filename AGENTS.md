# AGENTS.md — `ovos-solver-hivemind-plugin`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

An OVOS *question solver* plugin that exposes a remote HiveMind hub connection as
an answering backend. Given a query, it emits a `recognizer_loop:utterance` onto a
HiveMind connection (via `hivemind_bus_client`), waits for the hub's `speak`
responses, and returns them as the spoken answer. It registers under the OVOS
`opm.solver.question` entry-point group and is consumed by anything that chains
OVOS solvers, e.g. [ovos-persona-server](https://github.com/OpenVoiceOS/ovos-persona-server)
and [ovos-MoS](https://github.com/TigreGotico/ovos-MoS). Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — the hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the wire client
is [hivemind_bus_client](https://github.com/JarbasHiveMind/hivemind_bus_client).

## Layout / build / test

- Package module: `ovos_hivemind_solver/` (single-file solver in `__init__.py`
  plus `version.py`). Tests live in `tests/` — do not create a second test
  directory.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests -q`. Tests drive the
  solver through a real `HiveMindListenerProtocol` master via `hivescope`'s
  in-process topology simulator — no sockets, no live hub required. `hivescope`
  is a hard test dependency (declared in the `test`/`dev` extras); tests must
  never be `importorskip`'d around it.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a
  bug to FIX at the source, not to work around with a pin downgrade.

  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's

  instead; on your own PRs, edit the body rather than piling on comments.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- **This is a legacy solver plugin** (`opm.solver.question`), not an agent
  plugin. The modern OVOS pattern for this kind of integration is agent plugins
  (`opm.agents.chat`) — do not add new solver-based code elsewhere in this repo
  or port this pattern to other repos; treat this plugin as maintenance-only
  unless told otherwise.
- `HiveMindSolver.connect()` is the auth/session hot path: it opens the
  `HiveMessageBusClient` connection using credentials from the identity file set
  by `hivemind-client set-identity`. On failure to get an answer,
  `get_spoken_answer` must keep returning `None` (never raise) so the OVOS
  solver chain can fall through to the next solver — do not change this to
  fail loudly.
- Credentials (host, port, key, password) always come from the identity file;
  never add a code path that accepts them inline in `config`, and never log
  them.
- The `websocket_ping_interval`/`websocket_ping_timeout` keepalive kwargs are
  guarded by a `TypeError` fallback for older `hivemind_bus_client` versions
  (see the comment in `connect()`); when bumping the `hivemind_bus_client` floor
  past the version that always supports these kwargs, remove the fallback
  rather than leaving a dead compatibility shim.
- `test_no_neon_entry_point` in `tests/test_e2e.py` encodes an org-wide rule:
  never add a `neon.plugin.solver` entry point to this plugin.
